# Major revision plan: scheduling with costly, stale MEC state

Status: design plan, 15 October 2026. This file specifies work to be done; it does not report new experimental results.

## Research question and claim boundary

Can a deadline-aware vehicular-edge dispatcher improve critical-task completion under a fixed server-state signaling budget when its queue reports are delayed or lost? The proposed contribution is a **joint decision and reporting rule**: use timestamped, packet-delivered queue observations; request or send an update when the uncertainty could change a deadline-feasible server choice; otherwise dispatch using a conservative age-aware estimate. Measure the completion-versus-signaling tradeoff.

Stale load information, prediction, and practical server-information acquisition already appear in the literature. We will not claim to be the first to address stale information. The potential contribution is the combination of deadline-critical vehicular scheduling, decision-relevant report triggering, and packet-measured signaling cost, verified against close methods on the same workload.

The existing RAG-VERGE manuscript and outcomes remain archived as a separate prior study. The new paper is not allowed to reuse its reported gains as if they were obtained with packet-delivered telemetry or corrected mobility. Any LLM or RAG component, if retained, is a secondary ablation with a matched search budget, not the central claim.

## Phase 0 — repair the experimental substrate

1. **Vehicle activity.** Parse each SUMO vehicle's departure and arrival times and generate tasks only while that vehicle is present. Record active vehicles, offered tasks by time and class, and the exact observation window. Validate the same counts in SUMO and OMNeT++ on a short trace. Decide explicitly whether each departing vehicle is a client for its entire trip or whether tasks are generated by a sampled active subset.
2. **Immutable mobility.** Put map, trip seed, duration, route seed, and generator version in unique input paths. Hash the OSM extract, network, route, and movement trace. Refuse to overwrite archived 60-second inputs when generating longer traces. Use at least two independent trip seeds before any performance claim.
3. **Network semantics.** Inspect and trace the actual UE-to-MEC path. The current score includes a cross-cell penalty that may not be a measured path delay. Either implement and validate the path difference or remove that score term. Dynamic cell association and handover are currently disabled; do not label modeled boundary penalties as measured 5G handovers.
4. **Accounting and reproducibility.** Assign every offered task one outcome: deadline success, late response, explicit reject, lost response, or unfinished at the observation horizon. Separate primary task packets from state-report packets and any refresh requests. Make result directories immutable by study ID and input hashes; support safe resume. Preserve compact per-run records plus raw traces for audit cases.

**Exit gate:** One small paired run must show no tasks from inactive vehicles, task-count reconciliation, verified report/task packet routes, intact archived inputs, and all outcomes summing to offered tasks. If this gate fails, do not run the research matrix.

## Phase 1 — construct the minimal staleness experiment

1. Replace the process-global `advertisedEdgeFreeAt` vector in `src/TaskApps.cc` with per-client observations delivered through UDP packets. Reports carry server ID, sequence number, creation time, busy-until/workload, and capacity or service rate. Clients reject out-of-order reports. Measure report generation, delivery, loss, age at dispatch, and bytes on the modeled path.
2. Implement a periodic reporting reference with controlled periods, plus a zero-age fresh least-work reference clearly labeled as an unattainable comparator, not a performance bound. Keep the same server queue and task traffic for all policies in each paired seed.
3. Implement three minimal scheduling references: stale least-work/earliest-finish, random power-of-two using the same available observations, and a simple age-adjusted queue estimate. Add nearest and existing VERGE as contextual references only if their assumptions match.
4. Run a short screening matrix: two measured load regimes, three report periods, three non-oracle policies, and four paired network seeds (72 policy runs), plus a small number of oracle and no-report reference runs. Use at least two trip seeds in the follow-up validation. Measure **actual** offered load and report age; do not infer load solely from configured vehicle count.

**Go/no-go gate:** Confirm that delayed state materially changes decisions and completion in at least one nontrivial regime, and identify a meaningful completion-versus-signaling gap between the best deployable reference and fresh-state behavior. A simple age-aware rule is only a probe; if power-of-two dominates it, Phase 2 must beat power-of-two under matched cost. Inspect load oscillation rather than assuming stale state always hurts; prior work reports that it can sometimes desynchronize dispatchers beneficially. If there is no useful headroom, stop expansion and return to a corrected empirical paper.

## Phase 2 — develop one focused algorithm

1. Define an uncertainty interval for each server's current workload from report age, observed arrivals, capacity, and local reservations. Calibrate coverage on training traces and publish the coverage error on held-out traces.
2. At each critical-task decision, compare deadline-feasible servers under those intervals. Trigger a report or refresh only when uncertainty can change the chosen feasible server **and** the task has enough slack for the refresh to matter. Use a maximum report age as a safety fallback. Ordinary tasks use a lower-cost rule.
3. Fix the telemetry budget in advance. Compare policies at matched generated and delivered bytes/s, including refresh requests and duplicate messages. No policy may read simulator-internal future state.
4. Keep edge-side EDF/admission as a separate controlled factor. Test identical queue discipline across all dispatch policies first; add EDF/admission and its ablations only after isolating the dispatch effect. Never attribute an EDF gain to the telemetry algorithm.
5. Derive only results supported by the actual model: for example, a bound on workload-estimate error under stated bounded arrivals, or a sufficient condition for a refresh to change the robust server choice. Validate bound coverage empirically. Do not promise a universal herding threshold or hard deadline guarantee without proving its assumptions.

**Exit gate:** The full policy exceeds the strongest matched-cost baseline on the predeclared primary endpoint in validation cases, and each claimed component has an independently measured contribution. A negative result is reported, not hidden.

## Phase 3 — confirmatory evaluation

- **Design:** Freeze algorithm parameters after development. Reserve new paired trip and packet seeds for confirmation. Use a compact predeclared factorial over load, report period/loss, server heterogeneity, and policy; then targeted one-factor sweeps for RSU count, vehicle count, critical-task surge, and single-server failure. Begin with Downtown; add a second mobility area only if the main result survives its independent seeds. Avoid an indiscriminate thousands-run matrix.
- **Direct baselines:** Reimplement the applicable server-information and deadline scheduling mechanisms from Gao et al. (IEEE TVT 2025), predictive stale-load method from Hamid et al. (Network 2026), and a Beraldi-style stale-information load-balancing policy. Document each adaptation and validate on small examples. Zakerian's critical-first earliest-finish heuristic can serve as an additional scheduling reference if the online information constraints are aligned. An offline optimum, if used, is a labeled bound on small instances, never an online competitor.
- **Endpoints:** Primary: critical tasks completed by deadline divided by **all offered critical tasks**. Secondary: ordinary completion, response coverage, p50/p95/p99 latency with nonresponse stated, report age, report delivery/loss, signaling bytes/s and network share, server utilization/oscillation, drop/reject counts, fairness, decision cost, and performance around surges/failures. Plot completion against signaling cost, not just against report period.
- **Statistics:** Pair policies by identical mobility, task, and packet seeds. Report run-level differences and uncertainty intervals, not only pooled-task proportions. Predeclare one primary comparison, use multiplicity control for secondary comparisons, and expose all failed cells. Validate workload matching and no train/test leakage.
- **Infrastructure validity:** Distinguish simulated radio/transport delay from configured handover interruption. Dynamic handover becomes a separate study only after stability and packet-path checks. State task-size, service-rate, and deadline calibration sources; if empirical calibration is unavailable, label sensitivity settings as illustrative.

**Confirmation gate:** A robust primary effect must survive held-out paired seeds and close matched-cost baselines, without an unacceptable collapse in ordinary-task performance. If it does not, the honest publication path is a careful characterization or negative-result study rather than a superiority paper.

## Phase 4 — manuscript and artifacts

Rewrite the abstract, introduction, model, method, and evaluation around the validated claim. Add a related-work table that distinguishes state freshness, deadlines, packet-level telemetry, and signaling budget, without unsupported first-of-its-kind claims. Include a signal-flow diagram, a completion-versus-cost Pareto plot, load-by-age results, time series for surge/failure, outcome decomposition, tail-latency/coverage, calibration, and ablations **only where the data support them**. Do not add figures for page count. Provide code, immutable configs, hashes, exact versions, seed lists, raw audit traces, processed data, and a one-command runner with progress and safe resume. Compile and visually inspect the IEEE manuscript before any submission decision.

## Closest sources to verify and compare

- Gao et al., “Task Offloading and Scheduling Under Hard Deadlines in Vehicular Edge Computing Systems,” *IEEE Transactions on Vehicular Technology* 74(6), 2025, DOI 10.1109/TVT.2025.3539885. Practical server-information acquisition and hard deadlines.
- Beraldi et al., “On the impact of stale information on distributed online load balancing protocols for edge computing,” *Computer Networks* 210, 2022, DOI 10.1016/j.comnet.2022.108935. Theory and simulation of stale information and schedule lag.
- Hamid et al., “Exploiting and Mitigating Staleness in Distributed Edge Offloading via Predictive Load Awareness,” *Network* 6(3), 2026, DOI 10.3390/network6030069. Asynchronous delayed load broadcasts and predictors; staleness can help or hurt.
- Zakerian, “When Do LLM Agents Help? Deadline-Aware Mixed-Criticality Task Scheduling at the Autonomous-Vehicle Edge,” arXiv:2608.19557, 2026. Strong critical-first heuristic; LLM gain mainly under surge conditions.

## Immediate implementation order

Vehicle lifecycle and immutable trace IDs → packet telemetry and accounting → paired 72-run screening gate → method and ablations → held-out confirmation → paper rewrite. No full-scale campaign begins before the screening gate is reviewed.

## Evidence update, 16 October 2026

308 packet-telemetry runs are complete and audited. Analysis and seven plot
sets are in `analysis/packet_telemetry_v1`; see `PACKET_TELEMETRY_RESULTS.md`.
FreshPower2 has a positive mean Power2 contrast in nine of twelve cells,
but no exact paired comparison survives multiplicity correction; the extra
criticality penalty has no consistent incremental benefit. The 25/4, 75/4,
and 150/8 configurations are not the planned crossed scaling design.
Decision-triggered telemetry, independent mobility replications, deadline
admission, and literature algorithm reproductions remain incomplete.
This is progress through the exploratory gate, not completion of Phase 3.
